## 4. Per-Package Upgrade Assessment

### [High] multer 1.4.5-lts.2 → 2.1.1

- **Why now:** Vendor-side deprecation in npm registry. 1.x will not receive further security patches.
- **Breaking changes in 2.x (assessed against our usage):**
  - File-size error handling now throws instead of silently truncating — already aligned with our explicit `limits: { fileSize: 25 * 1024 * 1024 }`.
  - `req.file` / `req.files` shape unchanged for `.single()` and `.none()` (the only forms we use).
  - Async API normalized (Promise-based middleware available; classic callback form still works).
- **Call sites (`server.js`):** lines 159–160 (config), 863, 892, 920, 1756, 1935 (5 routes). All use `upload.single()` or `upload.none()`. No usage of `upload.fields()`, `upload.array()`, or custom storage engines, which is where 2.x gets harder.
- **Effort:** **2/5** — bump version, run regression test on each upload route (newsletter PDF, news-builder Word, news-builder file, SendGrid webhook, OPML import).
- **Risk of staying:** un-patched upload parsing in production accepting 25MB user files. Recommend completing this upgrade before the soft-launch traffic ramp.

### [Medium] stripe 14.25.0 → 22.1.0

- **Why:** 8 major versions behind. Stripe rotates API versions roughly quarterly and pins the SDK default to a snapshot. Staying on 14.x means our SDK default API version is from late 2023.
- **Breaking changes in our path (checkout, billing portal, webhook, customer create):** Stripe is unusually disciplined here — methods `stripe.customers.create`, `stripe.checkout.sessions.create`, `stripe.billingPortal.sessions.create`, `stripe.webhooks.constructEvent`, and the subscription/invoice event payload shapes have remained stable across 14 → 22. The main breaking change is **the pinned API version string** in the SDK constructor (we currently rely on the default — recommend pinning `apiVersion` explicitly during the upgrade so we control any data-shape drift).
- **Effort:** **2/5** — bump, add explicit `apiVersion`, regression-test the full payment path (checkout → webhook → subscription state in DB → portal → cancellation → reactivation). End-to-end test with a Stripe test-mode account is mandatory before production.
- **Risk of staying:** payment-path code on a 30-month-old SDK; new Stripe features (e.g., Tax automation, current adaptive pricing surfaces) are unavailable.

### [Medium] openai 4.104.0 → 6.35.0

- **Why:** 2 majors behind. v5 introduced the new Responses API and renamed several types; v6 stabilized it.
- **Breaking changes in our path:** **Only one call site in the entire codebase** — `server.js:1325` `openai.audio.speech.create({...})`. The `audio.speech.create` signature (`{ model, voice, input, response_format }`) is unchanged across v4–v6. Our LLM generation runs through Anthropic via raw `fetch` in `ai-service.js` and `agents/runtime/llm.js`, so the OpenAI SDK upgrade does not touch the AI generation path.
- **Effort:** **1/5** — single bump, single smoke test on TTS generation.
- **Risk of staying:** minor — TTS API has been stable. Mostly hygiene.

### [Medium] express 4.22.1 → 5.2.1

- **Why:** Express 5 GA'd in 2024 and is the long-term-support major. Express 4 is in maintenance.
- **Breaking changes:**
  - Async error handling is now native (no need for `asyncHandler` wrappers — but ours stay valid).
  - Path-to-regexp upgraded (some wildcard patterns differ; we use only standard `:param` patterns, no exotic patterns spotted).
  - `res.redirect` no longer accepts back URL by default; we use absolute paths so this is fine.
  - `req.param()` (deprecated in 4.x) removed — quick grep confirms we don't use it.
- **Effort:** **3/5** — three files touch Express, all middleware/routing patterns are vanilla. Risk is concentrated in subtle path-matching behavior and the helmet/rate-limit/validator middleware all being express-5 compatible (helmet 8 and express-rate-limit 8 explicitly support express 5; express-validator 7 already does).
- **Recommendation:** bundle this with the helmet 8 / express-rate-limit 8 upgrade as a single "express ecosystem" PR.

### [Low] helmet 7.2.0 → 8.1.0, express-rate-limit 7.5.1 → 8.4.1

- Helmet 8: stricter CSP defaults (we set our own CSP, so likely no impact — verify after bump).
- express-rate-limit 8: store-interface change (we use the in-memory default — no impact). The header naming is `RateLimit-*` per the IETF draft, which 8.x emits by default.
- **Effort:** **1/5** each. Bundle with Express 5 upgrade.

### [Low] pdf-parse 1.1.4 → 2.4.5

- pdf-parse 2.x switches to ESM-first and updates pdfjs-dist. We're already `"type": "module"`, so ESM is fine.
- **Effort:** **2/5** — single call site for newsletter PDF parsing. Smoke-test with a few real PDFs (text-only and scanned/image-only) to confirm output shape unchanged.

### [Low] dotenv 16.6.1 → 17.4.2

- dotenv 17 changes default behavior: no longer auto-overrides existing `process.env` values. We load early and don't conflict, so no impact expected.
- **Effort:** **1/5**.

### [Patch] nodemailer 8.0.5 → 8.0.7, express-validator 7.3.1 → 7.3.2

- Trivial patch bumps. Pick up on next routine `npm update`.
