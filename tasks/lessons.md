- **[2026-04-10] Dead CTA buttons shipped to prod**: The landing page's `.btn-primary / .btn-secondary / .btn-cta` handlers contained a `console.log('Button clicked', ...)` stub with the comment `"For now, just log (in production, these would navigate)"`. It shipped. Login link also had `href="#"`. Blog/terms/privacy pages pointed to `/login` which is not a route (server only serves `/app.html`). **Rule**: any time I ship a marketing/landing page, I must verify every interactive element has a real destination. Grep for `href="#"`, `console.log`, `// TODO`, and "for now" in any template before marking it done. Also: never use bare `<button>` for nav/CTA links — use `<a>` so broken JS still routes.

- **[2026-04-10] Rebrand rewrite replaced real API data with hardcoded mock newsletters**: Same `92b50d6 feat(brand): ship brv. logo` full-file rewrite not only broke the React CDN (see below) but also silently switched `App` from fetching `/api/newsletters` + `/api/tags` to hardcoded `mockNewsletters` (6 fake items: "Morning Brew", "The Information", etc.) and `mockTags` (5 colors). When the CDN was later fixed, users saw a working app — but one rendering placeholder demo data instead of their real 128 newsletters. User reported "all my newsletters have been lost"; they were never lost, the DB was fine, the UI just stopped asking. **Rules**: (1) a full-file rewrite of a working production file is an incident waiting to happen — always diff against origin/main before commit and scan for `mock*`, `sample*`, `fake*`, `placeholder`, `TODO` identifiers. (2) After touching a data-bound component, verify the live page shows data that matches what `/api/*` returns — don't assume "the page renders" means "the page works." (3) Normalize API field names at one chokepoint (a `normalize*` function), not inline at render sites, so snake_case ↔ camelCase mismatches can't hide in multiple places.

- **[2026-04-10] Full-file rewrite corrupted React CDN path → blank /app.html for everyone**: The `92b50d6 feat(brand): ship brv. logo` commit was a sweeping rewrite of `public/app.html` that accidentally changed `cdnjs.cloudflare.com/ajax/libs/react/18.2.0/umd/react.production.min.js` → `.../18.2.0/react.production.min.js` (dropped the `/umd/` segment). cdnjs returned 503 for the bad path, `React` and `ReactDOM` became `undefined`, and line 1 of the babel block (`const { useState, useEffect, useRef } = React`) threw a `ReferenceError` before anything rendered. Blank white screen. I then spent hours "fixing" auth wiring and adding an ErrorBoundary to diagnose — none of which could ever have helped because React itself wasn't loading. **Rules**: (1) NEVER do a full-file rewrite of a working production file — use targeted Edits so the git diff is reviewable. (2) After ANY change that touches `<script src>` or `<link href>` tags, open the deployed URL in Chrome MCP and verify `read_network_requests` shows every asset returning 200. (3) If a page goes blank, the FIRST debugging step is always `read_network_requests` + `read_console_messages` — check whether the runtime even loaded before touching application code. (4) Use unpkg.com (React's canonical CDN) with a jsdelivr fallback via `document.write`, so a single CDN outage never bricks the app. (5) Recognize the smell: "I'm adding instrumentation to understand a blank page" is a cue to re-check the basics, not to keep piling on code.

- **[2026-04-21] Proposed a parallel personal-digest script instead of actually using Brevis**: When Antonio asked how to integrate Brevis into his day-to-day, I described Month 1 item #1 as "a script runs on your Mac at 7am, pulls news from 5-10 sources, has Claude summarize and email you a digest." He correctly pointed out "that is not on brevis — it is something different." I had proposed a parallel tool that duplicates Brevis's core job. **Rules**: (1) When the ask is "integrate Brevis into X," the first question must be "what does Brevis already produce, and how do I route that into X?" — never "what new tool can I build that does roughly what Brevis does?" (2) The dogfood test: if the proposal still makes sense with Brevis removed, the proposal is NOT integrating Brevis. (3) For any Brevis-integration task, Antonio's correct starting point is subscribing to Brevis as a paying user and configuring his own account — the product's output is the source, not a thing to be re-built alongside.

- **[2026-05-04] Kill-switch verification command list assumed a row exists for the agent under test**: The Day-1 verification commands in `tasks/agent-stack-verification.md` told the operator to run `UPDATE agent_kill_switch SET enabled=false ... WHERE agent_name='hello'`. That migration only seeds the 7 production agent rows (editor, growth, sales, support, engineer, ops, orchestrator) — there is no row for `hello`. The runtime's `isAgentEnabled` (`agents/runtime/index.js:231`) defaults to `enabled=true` when no row is found, so a plain UPDATE silently updates 0 rows and the kill-switch test would be a false pass. Worked around by running `INSERT ... ON CONFLICT (agent_name) DO UPDATE SET enabled=false`. **Rules**: (1) Verification scripts that mutate-by-key must either seed the row first or use INSERT … ON CONFLICT, never a bare UPDATE. (2) When a safety rail's "off path" relies on row presence, write a unit test that exercises the no-row case and assert the documented default — that's where this footgun was hiding. (3) Updating the canonical command list in `tasks/agent-stack-verification.md` to use INSERT-ON-CONFLICT is a Day 2 cleanup item.

- **[2026-05-05] Tool names registered with dots failed Anthropic's tool API regex**: The Day-2 Editor agent's first real LLM call to Anthropic returned `400 invalid_request_error: tools.0.custom.name: String should match pattern '^[a-zA-Z0-9_-]{1,128}$'`. Tools were registered as `db.lookup`, `db.now`, `draft.create` — Anthropic's tool-name field rejects any character outside `[a-zA-Z0-9_-]`, including dots. The bug had been latent since the Anthropic provider was wired in: Day-1 hello agent passed because it used the stub provider; Day-2 in-sandbox checks (`tasks/verify-agent-stack.mjs`) tested template SQL and table shapes without actually round-tripping through the live Anthropic API, so the regex collision was never exercised. **Rules**: (1) Tool names are an *external contract* with the LLM provider — anchor them to the most restrictive valid charset across providers (Anthropic + OpenAI both share `[a-zA-Z0-9_-]`), don't smuggle convention-style separators through and hope. (2) Any wiring of a new provider must include at least one E2E test that actually round-trips through that provider's API — not just schema/template tests. (3) Enforce the contract at registration time, not at call time: `registerTool` now throws on any name that doesn't match `/^[a-zA-Z0-9_-]{1,128}$/`. Verified by running `registerTool({ name: 'newsletter.send', ... })` and observing the throw. (4) Same logic applies to any "stylistic but provider-validated" field — model names, parameter keys exposed to the LLM, etc. — anchor to the strictest valid form; don't rely on the wire to be lenient.

- **[2026-05-05] `agent_runs.cost_usd` double-counts because `finish` row writes a roll-up next to per-step rows**: Authoritative per-run cost from the runtime's `result.totalCostUsd` and the editor's `$0.1486` were both correct. But `SUM(cost_usd) FROM agent_runs WHERE run_id=X` returned `$0.2972` — exactly 2×. Cause: `runAgent` writes individual `cost_usd` values on each `llm_call` row, AND then writes the same total again on the closing `finish` row's `cost_usd` column. The budget guard's query (`SELECT SUM(cost_usd) ... started_at >= today`) inherits this 2× factor, meaning the daily cap rail trips at half its configured value. Editor's seeded $10/day cap is effectively a $5/day cap; ops's $1 cap is effectively $0.50. **Rules**: (1) Aggregate roll-ups and discrete spends must not share a column without a discriminator. The fix is either (a) write `cost_usd=0` on the finish row and put `totalCostUsd` in the payload only, or (b) change every aggregator to filter `step_kind != 'finish'`. Option (a) is cleaner because it makes the column's semantics single-purpose. (2) Cost / token / spend tables should be exercised by an actual paid LLM call before the rails depend on them — Day-1's stub provider had `cost_usd=0` everywhere, hiding this. (3) The doc query in the canonical command list now warns about this; the runtime fix is queued as a Day-3 prerequisite (we cannot trust the budget rail in production until it's applied).

- **[2026-05-05] Runtime's allowlist guard at `agents/runtime/index.js:143` is dead code under normal operation**: The Day-2 verification step "add `newsletter.send` to Editor's tools list, observe runtime block the call" silently passed — no error, Editor completed normally, draft persisted. Reason: `toolDefsForLlm(agent.tools)` filters allowlist names down to the registered set BEFORE the LLM call, so the API only ever sees tools that are both in `agent.tools` AND in the registry. Anthropic only returns `tool_use` blocks for tools we sent it. So the `if (!agent.tools.includes(call.name))` guard inside the dispatch loop can only fire if the LLM hallucinates a name not in its tools list, which Anthropic doesn't do. The actual allowlist enforcement is the silent filter in `toolDefsForLlm`. **Rules**: (1) Don't write defense-in-depth code that mirrors a guard that can't be bypassed — it gives a false sense of layered safety. Either prove a path that can bypass the upstream filter (none today) and keep the guard, or delete the guard and document where the real enforcement lives. (2) Verification tests should exercise the *actual* enforcement layer. For tool names, that's `registerTool`'s regex (verified separately) and `toolDefsForLlm`'s filter (verifiable by reading the `llm_call` payload's `toolCallCount` and confirming unregistered names produced no calls). (3) When a verification step "passes" without producing the expected error rows, that's a red flag, not a green one — re-read the code to confirm the test actually exercises the guard you think it's exercising.

- **[2026-06-10] Cut the overhaul branch from a stale local `main` — PR landed CONFLICTING**: `refactor/architecture-overhaul` was branched from local `main` (1f1b027) while `origin/main` was 4 commits ahead (PRs #2/#3 merged remotely via claude.ai/code sessions — they touched `server.js`, the exact file being refactored). The refactor therefore extracted routes from a stale base and silently dropped the webhook path-secret feature until the merge-back caught it. **Rules**: (1) Before cutting any long-lived branch: `git fetch origin && git checkout -b <branch> origin/main` — never branch from local main in this repo; remote merges happen without the local clone knowing. (2) This repo's PRs merge on GitHub (cloud agents, web sessions), so local main is stale by default — treat `origin/main` as the only truth. (3) After any refactor that moves code between files, `git diff <merge-base> origin/main -- <moved files>` to check for upstream changes that must be ported into the new locations.
