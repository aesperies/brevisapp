Brevis → Knowledge Graph Platform

Restructuring Plan — April 2026 | Inspired by Graphify (safishamsi/graphify)

EXECUTIVE SUMMARY
  • What: Transform Brevis from a newsletter reader into a personal knowledge graph platform — users forward newsletters, Brevis extracts entities & relationships, and builds an interactive, queryable graph that grows smarter over time
  • How: Adapt Graphify's two-pass extraction model (deterministic + LLM) for newsletter content, store graph data in PostgreSQL with JSONB (no new infra), visualize with vis.js, and make entity profiles configurable per user (VC/Legal vs. General)
  • Impact: This is a category-defining pivot — no competitor in the $2.53B newsletter tool market offers knowledge graph features. Estimated 3-week build to MVP.

1. What Graphify Does (& What We're Adapting)

Graphify's Architecture

Graphify is a Claude Code skill (3.6K+ GitHub stars) that turns any folder of code, docs, PDFs, or images into a queryable knowledge graph. Its core innovation is a two-pass extraction model:

PassWhat It DoesOur Adaptation for Newsletters
Pass 1: Deterministic AST parsing extracts code structure (classes, functions, imports) — no LLM needed Regex/NLP extraction of emails, URLs, dates, monetary amounts, company names from newsletter HTML
Pass 2: LLM Semantic Claude subagents extract concepts, relationships, and design rationale from docs/images in parallel Claude extracts entities (People, Companies, Deals, Topics) and relationships from newsletter content

Graphify's tech stack: NetworkX + Leiden community detection (graspologic) + tree-sitter + vis.js for visualization. Outputs: graph.html (interactive), graph.json (queryable), GRAPH_REPORT.md (audit).

Key insight we're borrowing: Graphify proves you don't need Neo4j or a vector database — PostgreSQL + JSONB + Leiden community detection gives you 90% of the value at 10% of the complexity. The graph topology itself is the similarity signal.

3. New Database Schema

New Tables (added to existing PostgreSQL)

-- Graph nodes: entities extracted from newsletters
CREATE TABLE IF NOT EXISTS graph_nodes (
    id SERIAL PRIMARY KEY,
    user_id INTEGER REFERENCES users(id) ON DELETE CASCADE,

    -- Core identity
    name VARCHAR(500) NOT NULL,            -- "Andreessen Horowitz", "Marc Andreessen"
    node_type VARCHAR(50) NOT NULL,        -- person, company, fund, deal, technology,
                                           -- regulation, topic, event, location
    canonical_name VARCHAR(500),           -- Deduplicated name ("a16z" → "Andreessen Horowitz")

    -- Rich metadata (schema-free, varies by node_type)
    metadata JSONB DEFAULT '{}',           -- { role: "GP", sector: "gaming", url: "..." }

    -- Graph metrics (updated by clustering job)
    community_id INTEGER,                  -- Leiden community cluster
    centrality FLOAT DEFAULT 0,            -- PageRank or betweenness centrality
    mention_count INTEGER DEFAULT 1,       -- How many newsletters mention this entity

    -- Timestamps
    first_seen TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    last_seen TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_graph_nodes_user ON graph_nodes(user_id);
CREATE INDEX IF NOT EXISTS idx_graph_nodes_type ON graph_nodes(user_id, node_type);
CREATE INDEX IF NOT EXISTS idx_graph_nodes_community ON graph_nodes(user_id, community_id);
CREATE INDEX IF NOT EXISTS idx_graph_nodes_name ON graph_nodes(user_id, canonical_name);

-- Graph edges: relationships between entities
CREATE TABLE IF NOT EXISTS graph_edges (
    id SERIAL PRIMARY KEY,
    user_id INTEGER REFERENCES users(id) ON DELETE CASCADE,

    source_id INTEGER REFERENCES graph_nodes(id) ON DELETE CASCADE,
    target_id INTEGER REFERENCES graph_nodes(id) ON DELETE CASCADE,

    -- Relationship
    relationship VARCHAR(100) NOT NULL,    -- "invested_in", "founded", "competes_with",
                                           -- "regulates", "acquired", "partnered_with"
    weight FLOAT DEFAULT 1.0,              -- Strength (incremented on repeated mentions)

    -- Provenance
    evidence JSONB DEFAULT '[]',           -- [{ newsletter_id: 123, excerpt: "..." }]
    is_inferred BOOLEAN DEFAULT false,     -- true = LLM-inferred, false = explicitly stated

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    last_seen TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_graph_edges_user ON graph_edges(user_id);
CREATE INDEX IF NOT EXISTS idx_graph_edges_source ON graph_edges(source_id);
CREATE INDEX IF NOT EXISTS idx_graph_edges_target ON graph_edges(target_id);

-- Link newsletters to the entities they mention
CREATE TABLE IF NOT EXISTS newsletter_entities (
    newsletter_id INTEGER REFERENCES newsletters(id) ON DELETE CASCADE,
    node_id INTEGER REFERENCES graph_nodes(id) ON DELETE CASCADE,

    -- Context
    excerpt TEXT,                           -- The sentence(s) where entity was mentioned
    sentiment VARCHAR(20),                 -- positive, negative, neutral
    relevance FLOAT DEFAULT 0.5,           -- 0-1 how central this entity is to the newsletter

    PRIMARY KEY (newsletter_id, node_id)
);

CREATE INDEX IF NOT EXISTS idx_ne_newsletter ON newsletter_entities(newsletter_id);
CREATE INDEX IF NOT EXISTS idx_ne_node ON newsletter_entities(node_id);

-- User's entity extraction preferences
CREATE TABLE IF NOT EXISTS graph_profiles (
    id SERIAL PRIMARY KEY,
    user_id INTEGER REFERENCES users(id) ON DELETE CASCADE,

    profile_name VARCHAR(100) NOT NULL,     -- "VC/Legal", "General", "Crypto", custom
    entity_types JSONB NOT NULL,            -- ["person","company","deal","fund","technology"]
    relationship_types JSONB NOT NULL,      -- ["invested_in","founded","competes_with"]
    extraction_prompt TEXT,                 -- Custom system prompt for Claude extraction
    is_active BOOLEAN DEFAULT true,

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_graph_profiles_user ON graph_profiles(user_id);

4. Entity Extraction Pipeline

Two-Pass Extraction (Graphify-inspired)

Triggered: Every time a newsletter is saved (email webhook, URL import, RSS fetch, file upload).

Pass 1: Deterministic Extraction No LLM Cost

Fast regex/pattern matching to extract structured data before sending to Claude:

// New file: graph-extractor.js

function deterministicExtract(content, title, sender) {
  return {
    // Email addresses
    emails: content.match(/[\w.-]+@[\w.-]+\.\w+/g) || [],

    // URLs with domain extraction
    urls: content.match(/https?:\/\/[^\s<>"]+/g) || [],

    // Monetary amounts ("$5M", "$100 million", "€2.5B")
    amounts: content.match(/[\$€£]\s?\d+[\d,.]*\s?(million|billion|M|B|K|mn|bn)?/gi) || [],

    // Dates
    dates: content.match(/\b\d{1,2}[\/-]\d{1,2}[\/-]\d{2,4}\b|\b(?:Jan|Feb|Mar|Apr|May|Jun|Jul|Aug|Sep|Oct|Nov|Dec)\w*\s+\d{1,2},?\s+\d{4}/gi) || [],

    // Potential company indicators (Inc, LLC, Corp, Ltd, etc.)
    companies: content.match(/[A-Z][\w&.'-]+(?:\s+(?:Inc|LLC|Corp|Ltd|GmbH|SA|AG|LP|Ventures|Capital|Partners|Labs|Studios|Games|Protocol|Foundation|Network|DAO)\.?)/g) || [],

    // Crypto tokens ($BTC, $ETH, etc.)
    tokens: content.match(/\$[A-Z]{2,10}\b/g) || [],

    // Sender domain (newsletter source)
    senderDomain: sender?.match(/@([\w.-]+)/)?.[1]
  };
}

Pass 2: LLM Semantic Extraction Claude API

Claude extracts entities, relationships, and sentiment in a single structured call:

// Added to ai-service.js

async function extractKnowledgeGraph(newsletter, profile, deterministicHints) {
  const systemPrompt = profile.extraction_prompt || DEFAULT_EXTRACTION_PROMPT;

  const result = await anthropicRequest({
    model: 'claude-sonnet-4-20250514',
    max_tokens: 2048,
    system: systemPrompt,
    messages: [{
      role: 'user',
      content: `Extract entities and relationships from this newsletter.

ENTITY TYPES TO EXTRACT: ${profile.entity_types.join(', ')}
RELATIONSHIP TYPES: ${profile.relationship_types.join(', ')}

DETERMINISTIC HINTS (pre-extracted):
${JSON.stringify(deterministicHints, null, 2)}

NEWSLETTER:
Title: ${newsletter.title}
Source: ${newsletter.sender}
<content>${newsletter.content.slice(0, 15000)}</content>

Return JSON:
{
  "entities": [
    { "name": "...", "type": "person|company|...", "aliases": [],
      "metadata": {}, "sentiment": "positive|negative|neutral",
      "relevance": 0.0-1.0, "excerpt": "..." }
  ],
  "relationships": [
    { "source": "Entity Name", "target": "Entity Name",
      "relationship": "invested_in|...", "is_inferred": false,
      "excerpt": "..." }
  ]
}`
    }]
  }, 45000);

  return JSON.parse(result);
}

5. Graph Processing & Clustering

Entity Deduplication

Critical for graph quality — "a16z", "Andreessen Horowitz", and "A16Z Crypto" should all be the same node:

// Entity resolution pipeline:
// 1. Exact match on canonical_name
// 2. Alias matching (stored in metadata.aliases)
// 3. Fuzzy match (Levenshtein distance < 3 for short names)
// 4. LLM disambiguation for ambiguous cases (batch, async)

async function resolveEntity(userId, entity) {
  // Try exact match first
  let node = await db.query(
    `SELECT * FROM graph_nodes
     WHERE user_id = $1 AND (canonical_name = $2 OR name = $2)`,
    [userId, entity.name]
  );

  // Try alias match
  if (!node.rows.length) {
    node = await db.query(
      `SELECT * FROM graph_nodes
       WHERE user_id = $1 AND metadata->'aliases' ? $2`,
      [userId, entity.name]
    );
  }

  // Create or update
  if (node.rows.length) {
    // Update: increment mention_count, update last_seen, merge metadata
    return await mergeEntity(node.rows[0], entity);
  } else {
    // Create new node
    return await createEntity(userId, entity);
  }
}

11. Risk Assessment

High
LLM Cost per Newsletter — Each extraction call uses ~2K output tokens (~$0.03/newsletter on Sonnet). At 100 newsletters/user/month × 1000 users = $3,000/mo in API costs. Mitigation: Gate behind Standard+ plan, cache extraction results, batch similar newsletters, use deterministic pass to reduce LLM load.
High
Entity Deduplication Quality — "a16z" vs "Andreessen Horowitz" vs "a]6z Crypto Fund III" — messy real-world data will create duplicate nodes. Mitigation: Alias system, periodic LLM-based dedup batch job, user-facing merge tool.
Medium
Graph Scaling in PostgreSQL — Graph queries (multi-hop traversals) are slower in SQL than graph DBs. Mitigation: For MVP, users will have <10K nodes — PostgreSQL handles this fine. Materialized views for common queries. Migrate to Neo4j/AGE only if we see performance issues at scale.
Medium
Extraction Quality Variance — Short newsletters may yield few entities; marketing newsletters may yield noise. Mitigation: Relevance scoring, minimum quality threshold, user feedback loop to improve extraction.
Medium
Frontend Complexity — vis.js graph + existing newsletter UI in one 7600-line HTML file. Mitigation: Keep graph as a separate tab/component. Consider extracting to a separate HTML file that loads in an iframe if it gets unwieldy.
